The purpose

A clearer place to investigate.

Normalize alert events into an existing Sentinel workspace so teams can investigate them alongside their security data.

What this project provides

3service-hook events: created, state changed, and updated
1custom alert table and a Sentinel workbook for triage
+active-alert backfill and an optional secret-alert rule

Architecture

From alerts to investigation.

Live events and active-alert backfill share one path into Microsoft Sentinel.

Processing flow & resilience

Deliver, retry, investigate.

Every queued event follows the same processing path, with explicit outcomes for success and failure.

Managed identity: storage + queue receive + DCR publish Raw events and locations excluded by default Service-hook send: queue SAS or service connection

Initial load

Start with the active picture.

A separate backfill utility seeds the same processing path with currently active alerts for one Azure DevOps project.

Delivery is at least once. Use EventId to deduplicate when querying.

Investigation

Turn records into useful context.

The workbook focuses on alert triage, with operational panels available when needed.

  • Review the latest event by repository, alert, and branch.
  • Optionally create incidents for new or backfilled active secret alerts.
  • Inspect Function traces and queue health when processing fails.
